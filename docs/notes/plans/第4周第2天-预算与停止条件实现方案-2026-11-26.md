1. 设置最大步数、工具调用次数、Run 累计 Token 预算和 Run 总时间预算。

3. 任一预算超限后进入确定性的 `budget_exceeded` 终止状态。
4. 保留相同工具、版本和参数的重复检测，增加通用无进展循环检测。
5. 将时间、随机数、模型响应和只读工具结果抽象为可录制依赖。
6. 明确真实模型重跑、确定性重放和故障重试之间的差异。

## 3. 总体设计

为每次 Run 创建独立的执行控制器，避免共享 Runtime 上的不同并发 Run 相互污染预算消耗和循环状态：

```text
RunInput
  -> BudgetResolver 解析用户 / 租户 / Run 三级预算
  -> 合并为 EffectiveBudget
  -> 创建本次 Run 的 BudgetController
       -> 步数控制
       -> 工具次数控制
       -> Token 累计
       -> 总时间控制
       -> 循环检测
       -> 依赖录制上下文
  -> Runtime / ToolLoopRuntime
  -> succeeded / failed / canceled / budget_exceeded
```

Runtime 负责流程编排，BudgetController 负责预算判断，RunStore 负责脱敏状态与事件记录，录制 Tape 负责原始依赖结果。四者职责不能混合。

## 4. 三级预算模型

计划在 `internal/agent/budget.go` 中逐步定义：

- `BudgetScope`：`user`、`tenant`、`run`。
- `BudgetLimits`：`MaxSteps`、`MaxToolCalls`、`MaxTotalTokens`、`MaxDuration`。
- `BudgetSet`：保存用户、租户和单次 Run 三组限制。
- `EffectiveBudget`：保存合并后的限制以及每项限制的来源作用域。
- `BudgetResolver`：由可信调用方根据 `UserID`、`TenantID` 和 `RunID` 提供预算。

预算不能来自模型输出、工具结果或其他不可信内容。

### 4.1 合并规则

1. 每个预算维度分别取三级配置中的最小正值。
2. `0` 表示该作用域未配置，负数或非法时间配置直接拒绝。
3. 合并后仍应用安全默认值，避免意外形成无限执行。
4. 保存每项限制的来源，例如 `token/user`、`steps/run`，用于解释停止原因。
5. 配置了用户预算但缺少可信 `UserID` 时，在调用模型或工具前失败。

初拟本地安全默认值：

| 预算 | 默认值 | 说明 |
| --- | ---: | --- |
| 最大步数 | 16 | 模型调用、工具执行和结构化修复均计步 |
| 工具调用次数 | 3 | 保持当前行为 |
| Run 累计 Token | 100,000 | 跨所有模型调用累计 |
| Run 总时间 | 2 分钟 | 从 Run 开始到最终收口 |

这些值只是本地安全默认值，不作为生产配额或性能结论。

`RunInput` 需要增加 `UserID`。当前它只表示可信内部调用方提供的身份，不代表已经实现 JWT 或 RBAC。

### 4.2 三级预算的本日边界

本日实现三级限制的解析、合并和对当前 Run 的执行约束。

用户或租户跨多个 Run 的持久化累计配额、原子扣减、恢复和公平调度，留待后续 PostgreSQL、Quota 和 Worker 阶段实现。本日不使用进程内计数冒充生产级共享配额。

为兼容当前代码，保留 `ToolLoopConfig.MaxToolCalls` 作为旧配置入口；未配置 `BudgetResolver` 时，将它映射为 Run 级工具次数限制。

## 5. 预算执行和停止语义

新增每次 Run 独立的 `BudgetController`，同时接入普通 Runtime 和 ToolLoopRuntime。

### 5.1 最大步数

一次以下操作计为一步：

- 一次模型调用；
- 一次工具执行；
- 一次结构化修复调用。

Prompt 渲染、配置查询和纯解析不计步。每次操作前检查预算，达到上限后不再发起下一次操作。

### 5.2 Token 预算

1. 跨分析、工具决策、最终回答等所有模型调用累计。
2. 优先使用供应商返回的真实 `Usage`。
3. 缺少 `Usage` 时使用确定性 Token 估算兜底并标记来源，不能把缺失用量当成零消耗。
4. 调用前检查剩余额度，并将本次 `MaxTokens` 限制在路由配置和剩余预算允许范围内。
5. 调用后立即结算，超过预算时停止后续解析、工具和模型阶段。
6. 修复调用没有真实 Usage 时，使用相同的确定性估算规则。

预算消耗与 `RunObservation` 中的真实供应商用量分开保存，避免把估算值冒充真实模型用量。

### 5.3 Run 总时间预算

1. 从进入 Run 开始计算，包含配置选择、模型、工具和最终回答。
2. 使用 `context.WithTimeoutCause` 创建 Run 级预算 Context，使阻塞中的模型或工具也能收到取消。
3. 每次模型调用的超时取路由单次超时和 Run 剩余时间的较小值。
4. 通过 Context Cause 区分调用方主动取消、调用方自身 deadline 和 Runtime 总时间预算耗尽。
5. 时间预算耗尽后禁止后续工具和模型调用。

总时间预算能够阻止后续副作用，但不能回滚已经开始的外部调用。当前高风险写工具仍由既有工具边界拒绝，本日不放宽该限制。

### 5.4 确定性终止状态

新增统一 `ErrBudgetExceeded`，并保留具体稳定原因：

```text
max_steps_exceeded
max_tool_calls_exceeded
token_budget_exceeded
total_time_budget_exceeded
```

错误只携带作用域、预算类型、限额和消耗量，不包含 Prompt、模型原文、完整工具参数或工具结果。

RunStore 增加：

- `RunBudgetExceeded = "budget_exceeded"`；
- `EventRunBudgetExceeded = "run.budget_exceeded"`；
- 预算限额、实际消耗、步数和来源作用域等脱敏信息。

MemoryStore 允许以下新增转移：

```text
running -> budget_exceeded
```

终态不可回退、不可重复完成，终态后不可继续追加事件。

普通失败仍为 `failed`，主动取消仍为 `canceled`。调用方 Context 超时不能被误记为 Run 总时间预算超限。

RunStore 写入失败仍按现有旁路边界通过脱敏回调报告，不改变已经确定的 Runtime 返回结果；验收时使用正常工作的 MemoryStore 验证终态和事件。

## 6. 循环检测

### 6.1 保留精确重复检测

继续使用当前稳定标识：

```text
工具名 + 显式版本 + 规范化参数 SHA-256
```

已有 JSON Map 键顺序稳定性、相同调用拒绝和 Executor 未调用测试必须保持通过。

### 6.2 增加通用无进展循环检测

1. 对“执行阶段 + 规范化后的模型决策”生成稳定摘要。
2. 同一工具循环中再次出现相同状态时，判定为无进展循环。
3. 能识别 `A -> B -> A` 等非连续重复，而不只是连续调用同一个工具。
4. 不同参数、能够产生新进展的决策不能被误判。
5. 检测发生在工具执行前，命中后不得进入 Executor。

新增稳定错误 `ErrLoopDetected`，观测分类为 `loop_detected`。循环保护失败仍进入 `failed`，不伪装成 Token 或时间预算超限。

## 7. 可录制依赖

新增独立的 `internal/recording` 边界。原始模型响应和工具结果进入依赖 Tape，不写入现有脱敏 RunStore。

### 7.1 录制条目

每条记录包含：

```text
RunID
Step
DependencyKind
RequestDigest
Payload
StableErrorKind
```

约束如下：

- `Step + DependencyKind` 决定消费顺序。
- `RequestDigest` 验证重放输入是否与原执行一致。
- 缺少条目、顺序错误、摘要不同或数据损坏必须明确失败。
- 不同 Run 的录制数据相互隔离。
- Tape 实现必须支持并发测试，但不能共享不同 Run 的消费游标。

### 7.2 四类依赖

| 依赖 | 抽象方式 |
| --- | --- |
| 时间 | 注入 `Clock`，Runtime、RunStore 记录和工具令牌校验使用一致的时间来源 |
| 随机数 | 将当前 HTTP request ID 使用的 `crypto/rand` 抽成可注入随机源，不改变 HTTP API 契约 |
| 模型响应 | 使用 `ModelCaller` 装饰器录制完整响应；依赖重放时返回录制响应，不访问供应商 |
| 只读工具结果 | 在 Tool 装饰边界录制 `ToolResult`；依赖重放时不调用底层数据源 |

工具录制仍必须经过：

```text
Registry.Resolve
  -> tooling.Invoke
  -> 权限 / 租户 / Run / Capability 校验
  -> 录制或重放 Tool
  -> ToolResult
```

只有 `EffectRead` 工具允许依赖重放。写工具在重放模式下必须在进入底层实现前明确拒绝，不能通过重放绕过安全边界。

### 7.3 敏感数据边界

1. 原始模型响应和工具结果只进入独立的录制 Tape。
2. 当前只提供进程内实现，用于确定性测试。
3. Tape 不写入 RunStore、Observer、普通日志或 Git。
4. Tape 不保存 API Key、Capability Token 或供应商原始错误文本。
5. RunStore 继续只保存摘要、版本、预算和运行元数据。

本日只验证依赖能够录制并按原顺序消费，不新增 `Runtime.Replay`，不提前实现第 5 天的 Checkpoint 和完整事件重放。

## 8. 真实重跑与确定性重放

统一以下术语：

| 方式 | 行为 | 确定性说明 |
| --- | --- | --- |
| 真实重跑 `rerun` | 使用原输入和配置快照，再次调用真实模型或依赖 | 不保证结果一致 |
| 确定性重放 `replay` | 消费原 Run 的录制时间、随机数、模型响应和只读工具结果 | 输入和录制一致时，依赖结果一致 |
| 故障重试 `retry` | 当前执行中的故障恢复策略 | 不属于历史重放 |

修正 `../../../internal/evaluation/demo.go` 中 `replayHistoricalRun` 的误导性命名和报告语义。该逻辑当前是使用确定性 Fake 再执行并比较配置版本，应明确标为 `rerun/config comparison`，不能继续作为确定性事件重放证据。

第 5 天才会基于本日依赖契约实现 Checkpoint、事件回放器和完整只读 Run 重放。

## 10. 测试和验收

至少覆盖以下场景：

1. 三级预算逐项取最小值，来源作用域正确。
2. 缺少用户身份、非法预算、默认值和旧 `MaxToolCalls` 兼容。
3. 步数、工具次数、Token 和总时间分别在恰好达到及超过时表现正确。
4. 超预算后不再调用下一个模型或 Executor。
5. 多次模型调用的 Token 正确累计，缺失 Usage 不会绕过预算。
6. Run 总时间能中断阻塞模型或工具，并能与外部取消区分。
7. 所有预算超限均只进入一次 `budget_exceeded`，事件和最终记录一致。
8. 终态不可回退，终态后不能继续追加事件。
9. 精确重复和 `A -> B -> A` 循环被阻止，正常不同参数调用不误判。
10. 时间、随机数、模型响应和只读工具结果可按录制顺序重放。
11. 重放缺少记录、请求摘要不匹配或数据损坏时失败。
12. 写工具重放被拒绝，底层写实现不会被调用。
13. 原始模型回答和工具结果不会进入 RunStore 或 Observer。
14. 并发 Run 的预算、循环状态和录制数据互不影响。
15. 真实重跑与依赖重放的调用次数和结果语义有自动化对比测试。
