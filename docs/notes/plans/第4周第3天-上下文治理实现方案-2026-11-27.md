## 2. 本日目标

为当前 `ToolLoopRuntime` 增加确定、可解释、可观测的上下文治理：

1. 裁剪过长的工具历史，避免每次决策都重复发送全部历史。
2. 对超长工具结果做确定性摘要和压缩，不增加模型调用。
3. 保留用户目标、任务分析、最新证据、失败原因和不可变配置快照。
4. 记录每次治理前后的 Prompt Token 估算、治理次数和上下文版本。
5. 将最终上下文指标同步到 Observer 和 RunStore 的脱敏观测。

本日不实现第 4 天的可信度标签、Prompt Injection 拦截或数据流安全策略，也不实现第 5 天的 Checkpoint、完整 Replay、事件回放器或 Fuzz 状态模型。Tape 继续按既有决定暂缓。

## 3. 当前问题与治理边界

当前 `toolHistory` 保存每次工具执行的结构化结果，`renderToolDecisionPrompt` 和 `renderToolLoopFinalPrompt` 每轮都调用 `encodeToolHistory`，把完整历史重新编码到 Prompt。随着工具次数和结果大小增长，会重复扩大模型输入并消耗 Token 预算。

本日只治理 ToolLoop 的动态工具历史。普通 `Runtime` 是固定的两阶段 Chain，没有多轮工具消息历史，不为其复制一套无实际作用的裁剪流程。

治理发生在**构建模型 Prompt 时**：

- 不修改原始 `state.toolHistory`；
- 不修改 `state.snapshot`；
- 不修改 ToolLoop 最终输出中的 `ToolCalls` 摘要；
- 不修改 Executor、授权、去重和 RunStore 工具事件；
- 不把完整工具原文写入 Observer 或 RunStore。

因此，上下文压缩是模型输入投影，不是对 Run 事实或配置历史的破坏性修改。

## 4. 总体设计

```text
原始 Query + 已校验 TaskAnalysis + 原始 toolHistory + 固定 ConfigSnapshot
                              ↓
                  构建未治理的 context.v1 基线 Prompt
                              ↓
                  对 toolHistory 创建独立治理副本
                       ↓                ↓
              单结果确定性压缩      历史条目裁剪
                       ↓                ↓
              保留最新结果和失败      非关键旧条目降级或省略
                              ↓
                  渲染最终模型 Prompt
                              ↓
             记录 before / after Token、次数和上下文版本
                              ↓
                 Observer + RunStore 最终脱敏观测
```

上下文治理由现有 ToolLoop 模型阶段调用，压缩和历史编码逻辑放入现有 `tool_loop_tools.go`，观测累加放入 `runtime_observation.go`。不新建生产文件。

## 5. 上下文策略

### 5.1 配置模型

计划在现有 `tool_loop_runtime.go` 中新增：

- `ContextPolicy`：可信调用方提供的本地上下文限制；
- `ToolLoopConfig.ContextPolicy`：可选配置入口；
- `ToolLoopRuntime.contextPolicy`：构造后固定，不在并发 Run 中修改；
- `ErrInvalidContextPolicy`：拒绝负数或其他非法限制。

初拟字段：

| 字段 | 含义 | 零值默认值 |
| --- | --- | ---: |
| `MaxHistoryTokens` | 可裁剪工具历史的目标 Token 上限 | 12000 |
| `MaxToolResultTokens` | 单个工具 Data 的压缩目标 | 2560 |
| `KeepLatestResults` | 始终优先保留的最新工具结果数量 | 10 |

`0` 表示使用安全默认值，负数返回 `ErrInvalidContextPolicy`。默认值只是本地执行策略，不作为模型质量或生产容量结论。

上限主要作用于可裁剪的历史内容。用户目标、任务分析以及保留条目的固定元数据不为了凑硬上限而删除。

### 5.2 上下文版本

使用稳定、可读的版本格式：

```text
context.v1:<ReleaseVersion>:h<MaxHistoryTokens>:r<MaxToolResultTokens>:k<KeepLatestResults>
```

例如：

```text
context.v1:release-v1:h12000:r2560:k10
```

该版本同时标识压缩算法、Run 配置发布版本和实际治理参数。同一 Run 内版本固定，不读取执行中变化的全局配置。

上下文版本不替代 `ConfigSnapshot`，也不作为新的控制面发布对象。

## 6. 保留规则

按以下优先级治理历史：

1. **用户目标**：`RunInput.Query` 原样进入工具决策和最终回答 Prompt，不裁剪。
2. **任务分析**：通过结构化校验的 `TaskAnalysis` 原样保留，不让模型摘要再次改写它。
3. **配置快照**：继续保存在 `toolLoopState.snapshot`，RunStore 配置版本引用不变，不把快照内容交给压缩器。
4. **最新证据**：最新 `KeepLatestResults` 条工具结果优先保留工具身份、状态、来源和压缩后的 Data。
5. **失败原因**：失败工具条目的 `Status`、`ErrorCode`、工具名称和版本始终优先保留，即使它不是最新条目。
6. **来源引用**：被保留条目的 `Source` 继续进入 Prompt，压缩 Data 时不把来源引用一并删除。
7. **非关键旧条目**：超出历史目标后，先降级为仅含元数据和来源的条目，再按从最旧到最新的顺序省略非固定条目。

这里“关键证据”采用明确、可测试的保留策略，即最新结果、失败结果及其来源；本日不声称本地截断能够理解任意工具数据中的所有语义重点。

被省略的条目数量需要进入模型可见的上下文元数据，避免模型把裁剪后的历史误认为完整历史。

## 7. 工具结果摘要和压缩

### 7.1 确定性本地算法

不调用模型生成摘要，避免增加额外模型步骤、Token、延迟和不可控改写。压缩只处理合法 JSON Data，并保持输出为合法 JSON。

超过单结果目标时，将 Data 投影为包含以下信息的受控对象：

```text
compressed       是否发生压缩
original_tokens  原始 Data 的本地 Token 估算
digest           原始 Data 的 SHA-256 摘要
preview          紧凑 JSON 的 UTF-8 安全预览
```

约束如下：

1. 先紧凑编码 JSON，再按 Unicode 码点限制预览，不能直接按字节截断 UTF-8。
2. 预览只进入当前模型 Prompt，不进入 RunStore 或 Observer。
3. 原始 Data 摘要用作一致性标识，不把它当作语义摘要。
4. 工具名称、版本、状态、错误码和参数摘要始终使用现有脱敏字段。
5. 非法工具 JSON 继续沿用 `ErrToolHistoryEncodingFailed`，不能通过压缩掩盖数据错误。

### 7.2 历史编码结构

将当前简单历史数组升级为带版本和裁剪元数据的受控 JSON 投影，至少包含：

```text
context_version
omitted_entries
entries
```

`entries` 中继续使用现有允许进入 Prompt 的字段，不直接序列化内部 `toolHistoryEntry`，避免未来新增敏感字段时意外暴露。

每次 Prompt 构建都从原始 `toolHistory` 创建新副本，不把上一轮压缩结果作为下一轮输入，避免多轮压缩造成累积信息损失。

## 8. Token 估算和观测

### 8.1 统计口径

对每次工具决策和最终回答 Prompt 分别计算：

- `before`：相同 `context.v1` 模板和历史 envelope 下，使用未治理完整历史时的 Prompt Token 估算；
- `after`：实际发送给模型的治理后 Prompt Token 估算。

统计包括 Query、TaskAnalysis、模板文本和历史，不只统计 Data。任务分析阶段的首次模型调用没有工具历史，不计入本日上下文治理指标。

Run 级字段采用累计口径：

| 字段 | 含义 |
| --- | --- |
| `ContextVersion` | 当前 Run 固定的上下文版本 |
| `ContextBuilds` | 已执行治理的决策和最终回答 Prompt 数量 |
| `ContextTrimmed` | 实际发生压缩、降级或省略的 Prompt 数量 |
| `ContextTokensBefore` | 各次未治理基线 Prompt Token 估算之和 |
| `ContextTokensAfter` | 各次实际治理后 Prompt Token 估算之和 |

这些值使用现有 `estimateTokenCount`，只用于上下文治理观测；不得写入供应商真实 `PromptTokens`、`TotalTokens` 或成本字段。

### 8.2 Observer 与 RunStore

在 Agent `RunObservation` 和 `runstore.RunObservation` 中增加上述五个脱敏字段，并由 `snapshotRunObservation` 复制。

本日不新增 Run 状态、事件类型或状态转移。上下文指标随既有最终观测写入 RunRecord，RunStore 写入失败仍只通过现有旁路回调报告，不改变 Runtime 返回结果。

如果 Run 在已完成至少一次 Prompt 治理后失败，最终观测仍保留已经产生的上下文指标和原有 `ErrorKind`。如果 Run 尚未绑定快照就失败，上下文版本可以为空。

## 10. 测试和验收

至少覆盖：

1. 零值默认策略、合法自定义策略和负数拒绝。
2. 短历史不省略条目，before/after 口径稳定，不发生无意义压缩。
3. 超长 Data 被确定性压缩，输出始终为合法 JSON，UTF-8 不出现截断乱码。
4. 工具身份、状态、错误码、参数摘要和来源在保留条目中完整保留。
5. 超出历史目标后先降级旧条目，再省略非固定旧条目，`omitted_entries` 正确。
6. 最新结果和失败结果优先保留，用户 Query 与 TaskAnalysis 原样保留。
7. 治理前后的 `state.toolHistory` 和 `ConfigSnapshot` 不发生修改。
8. 相同输入和策略得到相同历史 JSON、上下文版本和 Token 报告。
9. 工具决策与最终回答使用同一上下文版本，多次构建指标累计正确。
10. 压缩过程不增加 `ModelCaller` 调用、执行步数或真实供应商 Usage。
11. Observer 与 RunStore 字段一致，且不包含 Prompt、Data、preview 或完整工具结果。
12. Run 中途失败仍保留已经产生的上下文指标和稳定失败原因。
13. 并发 Run 的上下文版本、计数和 Token 报告互不影响，race 检查通过。
14. 现有授权、重复检测、预算、工具执行和输出测试全部保持通过。

## 11. 实施顺序和确认点

按以下依赖顺序实施：

1. `ContextPolicy`、默认值、配置校验和 Runtime 接线。
2. 上下文版本、治理报告和 Observer/RunStore 字段。
3. 单工具结果确定性压缩。
4. 历史降级、省略和版本化 envelope。
5. 工具决策与最终回答 Prompt 接入。
6. Observer 与 RunStore 指标记录。
7. 单元、集成、并发和回归测试。
8. 文档、证据和全量验收。

实际编码按完整阶段连续实施；每阶段集中补充相关测试，并在阶段结束后报告当前阶段、剩余阶段和验证结果。实施过程中未改变本方案的保留规则、公开配置或 RunStore 边界，也未扩大到第 4 天或第 5 天。
