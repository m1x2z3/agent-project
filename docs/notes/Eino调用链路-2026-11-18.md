# Eino 调用链路

## 本日目标

第二周第 1 天只验证 Eino 的最小编排能力，不接入真实供应商，不改变现有 HTTP API。

## 当前调用链

```text
Agent Input
  -> Prompt
  -> ChatModel
  -> Lambda
  -> Agent Output
```

本项目同时提供两种等价实现：

```text
Chain: Prompt -> Model -> Lambda
Graph: START -> Prompt -> Model -> Lambda -> END
```

## 组件职责

- `Prompt`：将业务变量渲染为模型消息。
- `ChatModel`：执行模型推理并返回消息；当前使用确定性 Demo Model。
- `Lambda`：执行确定性转换、输出校验和错误检查。
- `Chain`：表达固定的线性执行顺序。
- `Graph`：表达显式节点、边和后续可扩展的分支/并行关系。

## Context 与错误

- Pipeline 在入口先校验空问题，避免无效输入进入模型。
- `context.Context` 从 `RunChain`/`RunGraph` 传入 Eino，并继续传递到模型节点和 Lambda。
- 模型错误保持错误链，调用方可以使用 `errors.Is` 判断底层错误。
- Context 取消后，模型和后续 Lambda 不再继续生成结果。

## 边界取舍

- HTTP Handler 只依赖业务输入输出，不依赖 Eino 的 `schema.Message`。
- 供应商 HTTP 协议仍由 `internal/llm` 封装；本日不改造它。
- Eino 只负责编排组件，不负责租户权限、请求校验、审批和副作用安全策略。
- 参数校验、状态判断和输出整理必须由确定性代码完成，不能交给模型决定。
- 模型只负责推理和生成，不直接访问数据库、文件系统或外部网络。

## 直接调用与 Eino 编排

直接调用适合单一步骤、低复杂度和对延迟敏感的路径；代码更少，排查链路更直接。

Eino 编排适合需要 Prompt、模型、确定性处理、分支或并行组合的路径。它带来统一的
节点类型和 Context 传播，但也增加了编译、类型连接和运行时抽象成本。

当前选择是：保留 `internal/llm` 的供应商适配边界，在 `internal/agent` 内部引入 Eino。
这样后续可以增加结构化输出、工具调用和 Workflow，而不把框架类型扩散到 HTTP 契约。
