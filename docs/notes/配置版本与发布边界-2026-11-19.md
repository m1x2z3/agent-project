# 配置版本与发布边界

## 本日目标

第二周第 4 天新增独立的 `internal/configregistry` 包，使用内存实现验证
Prompt、Schema、模型路由和价格配置的版本发布、激活、回滚和 Run 快照绑定。

本日不接入数据库、HTTP 管理接口、灰度发布、影子运行或自动回滚。

## 控制面和数据面

控制面负责管理“哪些配置可以被使用”：

- 保存不可变的配置发布版本；
- 记录发布者、发布时间、生效时间和回滚关系；
- 激活某个发布版本；
- 查询历史版本；
- 为新 Run 绑定当前 active 版本。

数据面负责执行一次具体请求：

- 根据 Run 绑定的版本读取 Prompt、Schema、模型路由和价格配置；
- 调用模型、校验结构化输出和执行后续业务逻辑；
- 不应该在 Run 执行过程中悄悄读取最新 active 版本。

当前注册中心只在同一个 Go 进程内模拟控制面语义。后续接入 PostgreSQL 后，
需要把发布版本、激活状态和 Run 绑定放进事务和持久化表中。

## 为什么发布版本必须不可变

发布后的配置不能原地修改，否则历史 Run 会出现以下问题：

- 相同的 release version 在不同时间对应不同 Prompt；
- 结构化输出 Schema 发生变化后，旧结果无法解释；
- 模型路由或价格变化后，无法还原当时的调用决策；
- 回滚只能恢复部分字段，无法证明完整配置一致。

因此 `Publish` 只接受一个完整快照并保存副本，重复版本号直接拒绝。
`Get`、`Active` 和 `GetRunSnapshot` 都返回深拷贝，调用方修改返回值不会污染
注册中心内部状态。

## 激活、历史和回滚

发布和激活是两个动作：

```text
Publish
  -> 保存一个未激活的完整版本
Activate
  -> 将已发布版本切换为当前 active 版本
```

回滚也不会修改历史版本，而是复制目标历史版本创建一个新的版本：

```text
v1 -> v2 -> v3
          ^
          当前 active

回滚到 v1：
v1 -> v2 -> v3 -> v4
                  ^
                  新 active，RollbackFrom=v1
```

新回滚版本同时记录：

- `PreviousVersion`：回滚前的 active 版本；
- `RollbackFrom`：复制的目标历史版本。

这样回滚行为本身也成为可审计的发布记录。

## Run 快照绑定

Run 创建时调用 `BindRun(runID)`，注册中心只读取当时的 active 版本并保存深拷贝：

```text
创建 Run
  -> 读取 active=v1
  -> 绑定 Run 到 v1
  -> 后续激活 v2
  -> 该 Run 仍然使用 v1
```

这保证了后台发布新配置不会改变已经开始执行的 Run。
当前 Run 绑定仍然是内存数据，进程重启后会丢失，持久化和恢复留到数据库阶段。

## 与结构化输出的版本衔接

配置快照包含：

- Prompt 版本；
- Schema 版本；
- 模型路由版本，其中包含 provider 和 model；
- 价格版本。

`ConfigSnapshot.ResolveVersionReferences` 会把 Prompt、Schema 和任务路由整理成：

```text
provider
model
prompt_version
schema_version
model_config_version
```

调用方可以使用这些字段构造 `structuredoutput.ExecutionMetadata`。
`configregistry` 不直接依赖 `structuredoutput`，避免控制面包和执行内核形成反向耦合。

## 安全边界

`ModelRouteVersion` 只保存：

- provider；
- model；
- temperature；
- max tokens；
- timeout。

它不包含 API Key。API Key 继续由 `internal/config` 读取，并只用于构造模型客户端，
不会进入发布快照、历史记录、日志或提交记录。
