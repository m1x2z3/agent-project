# 工具注册与能力发现边界

## 本日目标

第三周第 3 天新增进程内工具注册中心，统一管理工具实例、工具版本和能力标签。
本日不接入 HTTP、MCP、数据库、RBAC、审批系统或 Agent 自动工具循环。

## 包职责

```text
internal/tool/tooling
  -> 工具公共契约、参数 Schema、Capability Token 和执行边界

internal/tool/readtools
  -> get_current_time、search_project_docs 等具体只读工具

internal/tool/registry
  -> 工具注册、版本发现、能力标签查询和定义快照管理
```

注册中心复用 `tooling.Tool` 和 `tooling.ToolDefinition`，不复制工具契约，也不依赖
具体的只读工具实现。注册中心保存工具名称、版本、定义快照和工具实例，调用方
必须显式指定版本：

```text
Registry.Resolve
  -> 返回 RegisteredTool
  -> 调用方构造 ToolExecutionRequest
  -> tooling.Invoke
  -> 确定性校验
  -> Tool.Execute
```

注册中心不会直接调用 `Tool.Execute`，因此不会绕过租户、Run、权限、资源范围和
Capability Token 校验。

## 名称、版本和能力标签

工具名称与版本共同组成唯一注册键：

```text
tool name -> tool version -> registered tool
```

相同名称的不同版本可以并存，相同名称和版本不能重复注册。版本只作为明确的
标识符使用，注册中心不比较版本号，也不推断哪个版本是“最新版本”；需要哪个
版本由调用方显式选择。

能力标签用于发现工具，例如 `read`、`project_docs` 或 `time`。能力查询按完整
标签匹配，并排除已废弃版本。`ListAll` 用于查看包括历史废弃版本在内的全部注册
内容；`ListAvailable` 用于默认发现，不包含废弃版本。

已废弃版本不会被立即删除，因为历史查询、兼容性排查和后续迁移仍可能需要它。
但它不会出现在默认可用列表，也不能通过 `Resolve` 作为可用工具返回。

## 为什么保存定义快照

`ToolDefinition` 包含 `json.RawMessage` 和切片字段。注册时复制这些可变字段，保证
调用方后续修改原始 Schema、租户列表或能力标签时，不会改变注册中心内部状态。
查询时再次复制返回值，保证调用方修改查询结果时，也不会污染后续发现结果。

锁只保护注册中心方法执行期间的并发访问；深拷贝保护的是方法返回之后的对象所有权。
两者解决的是不同问题，不能相互替代。

工具实例本身不做深拷贝，因为它可能持有数据源、连接池或缓存。注册中心只保存并
返回实例引用，真正执行仍然必须经过 `tooling.Invoke`。

## 与执行边界的区别

注册中心负责“找到哪个工具”，`tooling.Invoke` 负责“当前请求是否允许执行”：

```text
Registry
  -> 名称、版本、能力发现

tooling.Invoke
  -> 参数 Schema
  -> 租户与 Run
  -> Capability Token
  -> 权限和资源范围
  -> 风险与副作用边界
  -> Tool.Execute
```

模型生成的 `ToolDecision` 只有工具调用意图，不包含有效授权凭证。模型不能通过
自己生成的内容直接构造可执行的 `CapabilityToken`。

## 当前实现与后续边界

当前注册中心是进程内内存实现，使用读写锁保护并发注册和查询；没有持久化、跨进程
一致性、动态卸载或删除能力。当前也没有自动选择最新版本、自动升级、灰度切换或
自动回滚。

后续可以在保持 `tooling.Tool`、`ToolDefinition` 和 `tooling.Invoke` 边界不变的前提
下增加：

- 持久化注册中心和服务重启恢复；
- MCP Adapter，将外部 MCP 工具转换为本地契约；
- RBAC 和租户成员关系校验；
- 审批快照和高风险写操作授权；
- 面向 Agent 的能力发现与版本选择策略。

这些能力不应通过让注册中心直接执行工具来实现，否则会削弱统一的执行安全边界。
