# 预算与可录制依赖边界

## 1. 本次范围

第 4 周第 2 天的预算、停止条件、循环检测、时间与随机源注入、RunStore 脱敏预算元数据及 rerun/replay 术语修正已经实现，并通过全量测试、`go vet` 和 race 检查。

用户在 2026-11-26 明确决定：**录制 Tape 先不实现，以后再议。** 因此本文保留可录制依赖的边界说明，但不声称已经具备原始模型响应、工具结果录制或确定性 Replay。已有 Clock 和随机源注入可以独立用于确定性测试，不依赖 Tape。

## 2. 三级预算解析

`BudgetResolver` 从可信调用上下文提供用户、租户和单次 Run 三级限制，`BudgetSet` 保存输入，`EffectiveBudget` 保存实际生效值及来源。

每个维度独立合并：

1. `0` 表示该作用域未配置；
2. 负数或非法时间配置返回 `ErrInvalidBudget`；
3. 各维度取三级配置和安全默认值中的最小正值；
4. 保存 `user`、`tenant`、`run` 或 `default` 来源，用于解释终止原因；
5. 配置用户预算时，必须提供可信 `UserID`。

本地安全默认值为 16 步、3 次工具调用、100,000 Token 和 2 分钟。它们不是生产配额，也不代表用户或租户跨多个 Run 的累计配额；持久化扣减、跨进程一致性和公平调度不在本次范围内。

## 3. 每次 Run 的执行账本

`BudgetController` 在每次 Run 开始时独立创建，不放在共享 Runtime 上，因此并发 Run 不共享步数、工具次数或 Token 消耗。

### 3.1 步数与工具次数

一次模型调用、工具执行或结构化修复各计一步。模型和工具操作开始前检查时间及步数；工具进入 Executor 前还要检查工具次数。被拒绝的操作不计入消耗，也不会访问模型供应商或工具实现。

旧 `ToolLoopConfig.MaxToolCalls` 在未提供 `BudgetResolver` 时映射为 Run 级工具次数限制，保留原有调用兼容性。

### 3.2 Token 预算

Token 跨分析、工具决策、最终回答和修复调用累计：

- 供应商返回 `Usage` 时结算真实用量；
- 缺少 `Usage` 时按 Prompt 与实际响应文本执行确定性估算；
- 估算规则为非空文本每 4 个 Unicode 码点计 1 Token，向上取整；
- 调用后的消耗即使超限也必须先入账，再停止后续阶段；
- 恰好达到上限允许当前操作完成，但拒绝下一次模型操作；
- 超过上限时返回 `token_budget_exceeded`。

`MaxTokens` 在现有五个模型阶段直接取路由配置和当前剩余 Token 的较小值。预算账本中的 `BudgetTokens` 可以包含估算，Observer 与 RunStore 中的 `TotalTokens` 仍只表示真实供应商用量；`EstimatedTokens` 单独标记估算部分。

### 3.3 Run 总时间

Run 使用 `context.WithTimeoutCause` 建立总时间预算。单次模型超时取路由 Timeout 和 Run 剩余时间的较小值。Context Cause 为 `BudgetViolation` 时进入 `budget_exceeded`，调用方主动取消或自身 deadline 仍分别保留取消或超时语义。

时间预算能够中断阻塞调用并阻止后续副作用，但不能撤销已经开始的外部调用。

## 4. 确定性终止与 RunStore 元数据

统一预算错误为 `ErrBudgetExceeded`，结构化 `BudgetViolation` 只包含：

```text
Scope
Reason
Limit
Used
```

稳定原因包括：

```text
max_steps_exceeded
max_tool_calls_exceeded
token_budget_exceeded
total_time_budget_exceeded
```

RunStore 支持 `running -> budget_exceeded`，并追加 `run.budget_exceeded`。最终记录保存有效限额、实际步数、工具次数、预算 Token、估算 Token 和各限额来源；终止事件保存 `BudgetScope`、`BudgetLimit` 和 `BudgetUsed`。时间限额和消耗统一使用毫秒。

普通失败仍为 `failed`，主动取消仍为 `canceled`，循环检测失败仍为 `failed`。终态不可回退、不可重复完成，终态后不可继续追加事件。

## 5. 循环停止条件

精确重复检测继续使用“工具名 + 显式版本 + 规范化参数 SHA-256”，相同调用返回 `ErrDuplicateToolCall`。

通用检测在此基础上比较“执行阶段 + 规范化模型决策摘要”，补足授权版本变化等精确规则之外的重复状态，例如 `A -> B -> A`。相同版本、相同参数仍优先按精确重复处理；不同参数且能产生新进展的决策可以正常执行。

通用循环命中返回 `ErrLoopDetected`，Observer 分类为 `loop_detected`，不会伪装成预算超限。检测发生在 Executor 之前。

## 6. 时间与随机源

`internal/recording.Clock` 是请求级时间读取边界。未注入时使用 `SystemClock`；测试可以通过 `WithClock` 为每个 Run 注入独立固定或序列化时钟，避免真实 Sleep 和并发游标共享。

Runtime 预算、模型与工具耗时、RunStore 事件、MemoryStore 完成时间以及工具令牌校验使用同一请求 Clock。内部时间差保留 `time.Time` 的 monotonic 信息，外部 RunStore 时间再转换为 UTC。

HTTP request ID 使用可注入 `io.Reader`，生产默认 `crypto/rand.Reader`。响应仍保持 `req-` 加 16 位十六进制字符的格式，HTTP API 契约不变。

这些抽象目前支持确定性测试；没有 Tape 时，它们不等于完整的历史依赖录制和重放。

## 7. rerun、replay 与 retry

| 术语 | 当前含义 | 确定性边界 |
| --- | --- | --- |
| `rerun` | 使用原输入和配置快照再次执行模型或依赖 | 真实依赖重跑不保证结果一致 |
| `replay` | 消费原 Run 的录制时间、随机数、模型响应和只读工具结果 | 当前未实现 |
| `retry` | 当前执行中的故障恢复 | 不属于历史重放 |

`internal/evaluation` 中的历史逻辑已改名为 `rerunHistoricalRun`，结果字段为 `RerunConfigMatch`，报告明确标记为 `rerun/config comparison`。它只验证相同配置下的版本引用，不能作为确定性 Replay 证据。

## 8. 敏感数据与暂缓边界

RunStore 和 Observer 继续只保存状态、版本、摘要、预算数值、真实用量和稳定错误分类，不保存完整 Prompt、模型回答、工具参数、工具结果、API Key、Capability Token 或供应商原始错误文本。

本次明确暂缓：

- 内存 Tape 及录制条目；
- 顺序消费、请求摘要校验、缺项/乱序/损坏错误；
- 模型响应和只读工具结果录制/消费装饰器；
- 写工具重放拒绝及对应验收；
- 完整 `Runtime.Replay`、Checkpoint 和事件回放器。

因此，当前成果是预算和停止条件的完整本地实现，以及时间与随机源的确定性测试边界，不是完整的可验证历史重放系统。
