# 只读工具与数据源边界

## 本日目标

第三周第 2 天在 `internal/tool/tooling` 契约层之上实现两个只读工具：

- `get_current_time`
- `search_project_docs`

本日不接入 HTTP、Agent 自动工具循环、数据库、MCP 或写操作。

## 包职责

```text
internal/tool/tooling
  -> 工具契约、参数 Schema、Capability Token 和 Effect Boundary

internal/tool/readtools
  -> 具体只读工具、业务参数解析、数据源适配和脱敏观测
```

`internal/tool/tooling` 不知道具体业务工具；`internal/tool/readtools` 也不重复实现租户、
Run、权限和能力令牌校验。具体工具统一实现 `tooling.Tool`，执行入口保持：

```text
ToolExecutionRequest
  -> readtools.InvokeWithObservation
  -> tooling.Invoke
  -> 参数、租户、Run、版本、权限、资源范围和 Token 校验
  -> Tool.Execute
  -> ToolResult 校验
  -> 脱敏观测
```

模型生成的 `ToolDecision` 仍然只是调用意图，不能直接构造有效的
`CapabilityToken`，也不能绕过 `tooling.Invoke`。

## get_current_time

工具接收一个 IANA 时区，例如 `Asia/Shanghai` 或 `UTC`，返回：

- 格式化后的当前时间；
- 实际使用的时区；
- Unix 时间戳。

时钟通过构造函数注入。生产环境可以使用 `time.Now`，测试使用固定时间，因此
不需要依赖机器当前时间，也不会因为时区或执行时刻变化导致测试不稳定。

## search_project_docs

工具接收：

```text
project_id
query
limit
```

工具通过 `ProjectDocStore` 查询数据，不直接依赖 PostgreSQL、pgvector 或 HTTP。
当前的 `MemoryProjectDocStore` 具备：

- 租户和项目双重过滤；
- 大小写不敏感匹配；
- 稳定的文档 ID 排序；
- 结果数量限制；
- 项目不存在与空搜索结果的区分。

工具在业务层再次确认资源范围包含 `project:<project_id>`，用于保证能力令牌授权
的资源边界与实际查询目标一致。

## 错误和观测

业务错误统一转换为 `ToolResult`：

| 场景 | 结果状态 |
| --- | --- |
| 参数或时区非法 | `invalid_argument` |
| 项目不存在 | `not_found` |
| 项目资源范围不足 | `forbidden` |
| 数据源超时 | `timeout` |
| 数据源内部错误 | `internal_error` |
| 查询成功 | `success` |

观测只保留：

```text
tool_name
tool_version
request_id
duration_ms
result_status
error_code
arguments_digest
```

参数使用 SHA-256 摘要，不保存原始参数。`InvokeWithObservation` 只对执行前被
`tooling.Invoke` 拒绝的请求补充观测；具体工具已经开始执行后，由工具自身记录，
避免一次调用产生两条记录。

## 当前边界

当前只读工具仍是可替换的内存和接口实现：

- 没有接入 PostgreSQL、pgvector 或真实文档索引；
- 没有工具注册中心和自动工具发现；
- 没有接入 Agent Runtime 的自动工具循环；
- 没有实现 JWT、RBAC 和持久化防重放；
- 没有实现 MCP Server/Client；
- 没有实现写工具、审批或外部副作用。

这些能力将在后续计划中逐步接入，不能把当前只读工具实现误认为完整生产工具
平台。
